## SHARED LIFECYCLE
Execute `pipelines/_shared/semantic-document-lifecycle.md` exactly. The steps below specialize that lifecycle for summaries and add summary-only visual stages. They do not replace or weaken any shared review, gate, publication, environment or failure requirement.

## RUNTIME BOUNDARY
Visual support must not turn summary generation into an open-ended graphics session.
- Exact diagrams stay on the compact deterministic schema-1 path; the model never authors raw SVG or explicit coordinate scenes.
- Optional generated illustrations use one compact semantic spec and one bounded provider call. There is no independent per-illustration vision-review loop.
- A provider outage never justifies repeated image retries or weaker academic prose.
- `visual_not_needed` remains a pedagogical decision, never a runtime shortcut.
- A standard run beyond roughly 30 minutes is a performance warning; 60+ minutes is a product/runtime failure.

## DEPTH
`resumen` is the single public long-form study-document action.
- Default depth is `standard`: balanced, self-contained notes for normal study.
- If the caller explicitly asks for `detallado`, `profundo`, a former “guía”, or equivalent wording, use `detailed`: preserve the exact same academic scope and gates, but allow more explanatory scaffolding, examples, contrasts and prerequisite reminders where they improve understanding.
- Detailed mode must not invent extra syllabus scope, reread raw sources merely to add volume, impose a fixed length, or become an exhaustive transcript rewrite.
- Record the chosen depth in `02-plan.json` as `depth: "standard"|"detailed"`. The published artifact remains the unit's canonical `resumen`; detailed mode replaces the previous public `guia` action instead of creating a parallel document type.

## Pipeline-specific RUN specialization
1. **SCOPE + PREREQUISITE** → resolve course + scope to exactly one stable `unit_id`; summary scope is unit-only. Resolve optional depth intent before starting the run; only explicit detailed/guide wording selects `detailed`, otherwise use `standard`. If Study MCP is connected, call `study_get_unit_context(course, scope)` once and `study_list_artifacts(course)` instead of manually reopening/filtering canonical JSON. Otherwise use only the files below `unidades/<unit-id>/` plus explicit cross-unit prerequisites. Refuse an unresolved/global pedagogical scope. Apply the shared **NEEDS_INGESTION** boundary before starting a run. Run `python scripts/venv_exec.py study.py figures migrate <course>` once; it only normalizes legacy derived-figure metadata and does not reread/reprocess sources.
2. **START RUN** → `python scripts/venv_exec.py scripts/pipeline_run.py start --course <course-folder> --pipeline resumen --scope "<scope>"`. The run records deterministic fingerprints of the study engine and canonical academic/concept/topic/figure inputs. Apply the shared active-run isolation rules. Summary-specific figure mutations are allowed only through the planned visual build described below.
3. **PLAN** → write `02-plan.json`, including `depth`. Use canonical knowledge, not raw transcript prose, to decide central idea, ordering, required examples, traps and omissions. Use observed topics as a flexible coverage map so concept blocks are not overlooked, while preserving declared syllabus topics as a separate academic reference. Topic boundaries may guide or combine sections; they never impose a fixed section count, order or length. In `detailed` mode, explicitly identify which concepts deserve extra explanation/examples and why instead of expanding every section uniformly. For every major concept decide `visual_required`, `visual_helpful` or `visual_not_needed`; for every selected visual record the treatment and provenance required by the plan visual contract. `flow`, `tree`, `concept-map`, `relations` and `technical-schematic` use `reinterpret` by default whenever all meaningful structure can be reconstructed, even if a source PNG exists. `source-first` selects evidence, not final pixels. `preserve` or `preserve+derived_sketch` requires a non-empty `fidelity_reason` naming the exact precision-sensitive detail that needs the original. For a derived `reinterpret`, choose `visual_medium`: exact structure/flow/cycle/timeline/hierarchy/relationship uses `diagram` and a validated structured spec under `<run-dir>/02-sketches/`; a recognizable physical/conceptual likeness that only supports the prose may use `illustration`, must be `visual_helpful`, and uses only the compact semantic illustration object in `contracts/handoffs.md`. `preserve+derived_sketch` remains a deterministic `diagram`; `preserve` must not create a derived spec. Generated illustration pixels never carry exact labels, arrows, quantities, chronology, topology, formulas or assessment-critical facts. Select only figures that add instructional value. Do not write polished prose, raw SVG, coordinates or provider prompts here.
4. **VISUAL BUILD** → before drafting, run `python scripts/venv_exec.py scripts/visual_plan_hybrid.py --course <course> --unit "<scope>" --plan <run-dir>/02-plan.json --write <run-dir>/02-visual-build.json`. This stage validates every visual decision. For `visual_medium: diagram`, the hybrid materializer delegates to the proven deterministic backend in `scripts/visual_plan.py`, which registers the derived SVG and records the exact asset/spec hashes. The underlying per-spec operation remains `study_generate_sketch_figure(course, unit, spec)` / `study.py figures generate-sketch`; never create normal diagrams with an image-generation model. Illustration entries use one bounded provider call from the compact semantic spec, then deterministic crop/background removal and transparent notebook-overlay registration. Exact diagram retries and exact registered illustration/spec reuse are idempotent; collisions fail closed. Keep every `preserve` source asset unchanged. Do not edit `figures.json` directly, do not edit a source figure record into a derived one, and never overwrite an existing id/asset. If an illustration provider is unavailable, do not retry repeatedly: make at most one plan fallback for that optional visual, switching to a deterministic diagram only when the same supported meaning is naturally diagrammable, otherwise mark the illustration `visual_not_needed` for this run and rerun the build once. Stop if the final report is not `ok: true`.
5. **DRAFT** → write `03-draft.md` from the plan, canonical knowledge and successful `02-visual-build.json`. The draft must stand alone for a student who has not read the sources. Standard mode should stay balanced and efficient. Detailed mode may develop difficult concepts more fully, add useful contrasts and prerequisite reminders, but must preserve the same unit scope and avoid encyclopedic padding. Use semantic callouts and the exact registered `asset` returned for each plan entry; a `reinterpret` must reference its derived asset, never its source PNG. A generated illustration supplies recognition only and must not be cited as evidence for an exact claim. Place a figure beside the explanation it supports.
6. **REVIEW** → in addition to the shared independent review contract, evaluate the candidate against `02-plan.json`, `02-visual-build.json`, the figure registry/assets and all required rubrics, including visual support. Fail the review if the Markdown treatment differs from the plan. Write the review using the full fidelity-check contract in `contracts/handoffs.md`. Detailed mode gets no lower fidelity threshold and no permission to add unsupported context. Do not start a separate image-aesthetics review cycle; a relevant, recognizable, non-misleading optional illustration does not need regeneration for style preference.
7. **RENDER CANDIDATE** → render the shared accepted Markdown with `python scripts/venv_exec.py scripts/render_study.py <accepted-md> <run-dir>/09-rendered.html --kind summary --course "<course-display-name>" --scope "<scope>" --check`. Caption metadata may have blank lines after tables/code; orphan captions are a hard render check failure. Generated illustrations are registered as transparent notebook overlays; the page itself remains real HTML/CSS.
8. **INTEGRITY GATE** → use `study_validate_artifact(..., plan=<run-dir>/02-plan.json)` when Study MCP is connected, otherwise `python scripts/venv_exec.py scripts/artifact_integrity.py --course <course> --markdown <accepted-md> --html <run-dir>/09-rendered.html --scope "<scope>" --type summary --plan <run-dir>/02-plan.json --write <run-dir>/10-integrity.json`. In either path, persist the result as `<run-dir>/10-integrity.json`. Besides image paths, captions, registry provenance and stable unit scope, this gate binds every final figure to the plan: a diagram `reinterpret` must use the registered deterministic SVG; an illustration `reinterpret` must use the registered generated-illustration asset; neither may silently substitute a source asset; `preserve+derived_sketch` must use both.
9. **BROWSER VISUAL GATE** → run `python scripts/venv_exec.py scripts/visual_audit.py <run-dir>/09-rendered.html --out <run-dir>/visual-audit` and apply every shared browser-visual requirement. This gate must not be replaced with HTML-string or image-path checks. In the screenshot inspection, specifically reject obvious hierarchy, clipping, figure-legibility or spacing defects that mechanical metrics cannot express, plus generated illustrations that visibly introduce misleading text/labels. Browser auditing is final integration QA, not an open-ended image-regeneration loop.
10. **ATOMIC PUBLISH** → resolve `<publish-dir>` as `unidades/<unit-id>/resumenes`, then after all shared gates pass run `python scripts/venv_exec.py scripts/publish_artifact.py --markdown <accepted-md> --html <run-dir>/09-rendered.html --dest-markdown <publish-dir>/_source/<scope>-resumen.md --dest-html <publish-dir>/<scope>-resumen.html --report <run-dir>/11-publication.json`. Apply the shared immutability/hash rules; do not publish with generic copy/edit operations.
11. **MARK** → mark the published HTML with `study_mark_artifact` when MCP is connected or `python scripts/venv_exec.py scripts/artifact_state.py mark --type summary --scope "<scope>"` otherwise.
12. **FINISH** → `python scripts/venv_exec.py scripts/pipeline_run.py finish --run <run-dir>`. In addition to the shared finish contract, summary finish mechanically rejects missing/corrupt visual-build/publication evidence, any engine mutation, any academic/concept/topic change, every source-figure edit/removal and every unplanned figure registration. It permits only append-only derived records whose ids/treatments match `02-plan.json` and `02-visual-build.json`.
